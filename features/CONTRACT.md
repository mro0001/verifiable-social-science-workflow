# The features' contract

The features lower the cost of adopting and learning the workflow (proposal Overview paragraph 3, appendix A2.7 and Table A8). Pipeline setup checks and records the scholar's software and harness once per scholar, then lays out a reproducible project once per project. The project organizer lets the scholar's AI session propose changes to a project's files, builds, and past sessions, applies them only when the scholar runs the apply command, and undoes any of them. The portal is a static site where a scholar learns the workflow, finds how to set it up, and writes a critique of any page. Custom skills need nothing built, since each enters as its own program with a declared contract.

This file states what the package takes in, what it gives back, and which promises are frozen. Each later step fills in its command's section.

## How it runs

`python3 -m features` from the repository root, with three command groups, `setup`, `organize`, and `portal`. `python3 -m features --version` prints `features 0.1`. A group given with no command prints its help.

## How it reaches the other layers

Only through their command lines and their files. `layers.py` is the one place a command of another layer is run.

| Layer | Command run | Environment and folder |
|---|---|---|
| `ospipe` | `python -m ospipe ARGS` | `<root>/ospipe` first on `PYTHONPATH` |
| `audit_layer` | `python -m audit_layer ARGS` | `<root>` first on `PYTHONPATH` |
| `vg` | `python <root>/verification_procedures/vg.py ARGS` | run in `<root>/verification_procedures` |
| `connections` | `python -m connections ARGS` | `<root>` first on `PYTHONPATH` |

The root is the folder that holds `features/` unless one is given. `run_layer` gives back the argument list, the exit code, and both outputs, and returns a nonzero exit instead of raising it. It raises `LayerMissing` naming the folder or script when `<root>/ospipe/ospipe`, `<root>/audit_layer`, `<root>/verification_procedures/vg.py`, or `<root>/connections` is absent. `LAYERS` names the first three, which system setup checks by their help, and `RUNNABLE` adds `connections`, whose `provider set` system setup runs (step S2).

## Commands

### setup

Software detection is in `setup/detect.py`. It looks for the scholar's software and reports what is found, its version, and whether it meets the workflow's minimum. It writes no file, runs no layer command, and installs nothing. For anything missing it gives a plain install line to print. Every outside program is started only through its one runner function, `run_program`, so a test replaces it with a stand-in.

| Software | Kind | Required | Looked up by |
|---|---|---|---|
| `python` | language | yes, 3.9 or later | the running interpreter |
| `pyyaml` | package | yes | its installed package version |
| `python-docx` | package | yes, 1.2 or later | its installed package version |
| `pytest` | package | yes | its installed package version |
| `pandoc` | build | yes | `pandoc --version`, with a note when it is not 3.9.0.2, the version the stored test builds were made with |
| `make` | build | yes | `make --version` |
| `git` | version_control | no | `git --version` |
| `gh` | version_control | no | `gh --version` |
| `quarto` | build | no | `quarto --version` |
| `rscript` | statistics | no | `Rscript --version` |
| `word` | editor | no | the folder `/Applications/Microsoft Word.app`, with no version |
| `zotero` | citations | no | the folder `/Applications/Zotero.app`, by its existence alone |
| `zotero_data` | citations | no | the folder `~/Zotero`, by its existence alone |
| `claude_code` | harness | no | `claude --version` |
| `forgecode` | harness | no | `forge --version` |

Zotero is looked for by its folders existing, and nothing inside them is opened. The scholar names the export file during system setup.

`detect_state` finds what is already set up, writing nothing. It reads git's `user.name` (`git config --global --get user.name`), whether `WORKFLOW_MODEL_KEY` is set (never its value), the `excluded_folders` listed in `<audit home>/settings.yaml` (read only), the events of `~/.claude/settings.json` that hold the workflow's capture command (`audit_layer/hooks/claude_code_hook.py`) or trigger command (`connections trigger hook`), and which of `workflow-kb`, `workflow-audit`, and `workflow-events` the output of `claude mcp list` names. `git_user_name()` gives git's `user.name` alone, through the same runner, for system setup when the answers leave out the name.

#### setup system

`python3 -m features setup system [--home DIR] [--audit-home DIR] [--answers FILE]`, once per scholar, in `setup/system.py`.

- The features home is `--home`, else `FEATURES_HOME`, else `~/.workflow_features`. The audit home is `--audit-home`, else `AUDIT_HOME`, else `~/.audit_layer`. The connections home is `CONNECTIONS_HOME`, else `~/.workflow_connections`.
- Answers come from the `--answers` YAML file, else from questions asked one at a time in the terminal in the order and words of `setup/decisions.py` (step S2). The excluded folders come first, one full path a line, where a path not starting with `/` or `~` and an empty first line are asked again and the word none gives none. The name follows only when git's `user.name` is empty, an empty name being asked again. Then come the model service (a web address, asked again when it does not start with `http://` or `https://`, Enter to skip), the model (Enter skips the service), and the second model (Enter to skip, asked again when it equals the model), proposed from the first other id in `<model service>/models`, the one request setup makes, sent with the key as a bearer token when `WORKFLOW_MODEL_KEY` is set. Last come the citation export, and the harness only when neither `claude` nor `forge` is found, where Claude Code and ForgeCode give their names, Enter gives none, and anything else gives `another`. With neither a file nor a terminal the command refuses, names the fields, and exits 2.
- The fields are `scholar_name` (may be left out when git's `user.name` is set), `harness` (`claude_code`, `forgecode`, or `another`, defaulting to `claude_code` when `claude` is found, else `forgecode` when `forge` is found, else empty, recorded as empty and printed as `Harness not found` with both install lines), `excluded_folders` (a list of full paths that may be empty), `citation_export` (the BibTeX file the citation manager exports, or empty), `model_service`, `model` (given with `model_service`), `second_model` (other than `model`), `token_limit` and `token_limit_field` (given together), and `connect` (yes or no, no when left out). An answers file must give `excluded_folders` and no other field than these.
- Before writing anything, setup prints the review screen. It lists what was found and what each finding gets, the six defaults (the light check, full reports, the live view, session titles, the online lookup, and capture from the day of setup), and each change it would make outside the workflow's own homes, leaving out the capture hooks, the trigger hooks, and the servers already in place. These are the capture and trigger hooks in `~/.claude/settings.json` and the three server registrations when Claude Code is found, the 30-minute schedule (a launch agent on a Mac, a crontab line elsewhere) when either harness is found, and the wrapper block in the shell profile. It ends with the one yes, asked in the terminal (Enter says yes) or read from `connect`. Until steps S5 to S8, setup makes none of these changes, records the answer as `connect` in `system.yaml`, and prints the hand steps that remain.
- Setup detects the software and checks that `ospipe`, `audit_layer`, and `vg` each answer `--help`. Its first write lists the excluded folders, those answered and those an earlier run recorded, in the audit settings through `python3 -m audit_layer excluded add --home <audit home>`, which adds and never removes. With no folders it runs `audit_layer init` with `AUDIT_HOME` set only when `<audit home>/settings.yaml` is absent. It stops with either command's error when it fails. When a model service is given, it then writes `provider.yaml` again through `python3 -m connections provider set ... --home <connections home>`, never with a key. That command replaces the file whole. When the answers give no `token_limit`, setup reads an earlier `provider.yaml` read only and passes its `token_limit` and `token_limit_field` on, the field taken as `max_tokens` when the file names none, and the report says the limit was kept. An earlier file setup cannot read, or a limit in a form it cannot use, is named in the report and not kept. It records each excluded folder, with `~` expanded and made absolute, in `system.yaml`, keeping every folder an earlier run recorded and listing each once. It checks that a given citation export exists and says so when it does not. When an earlier `system.yaml` cannot be read (malformed, of another schema or version, lacking a field, or with `excluded_folders` not a list), setup stops with exit 1 before it runs anything, leaves the file as it is, and names the file with the advice to repair it or move it aside, since setup will not drop the folders recorded there.
- It writes `<features home>/system.yaml` with `schema` (`features-system`), `schema_version` 1, `written_at`, `workflow_root`, `python`, `scholar_name`, `harness`, `audit_home`, `citation_export`, `excluded_folders`, `connect`, `layers` (each of the three with `ok`), `ready` (false when a required tool or a layer is missing), and `software` (one row per tool found or not).
- It prints each tool with its version or install line, the three layers, the harness, the audit home, the excluded folders with the settings file that lists them, the provider setting written, and, when a service is given and `WORKFLOW_MODEL_KEY` is not set, the one `export` line to add to the shell profile. Then come the later connections this package does not make yet, naming `audit_layer/hooks/INSTALL.md` and `connections/README.md` for the hand steps and observability for the live view, the path written, and `Ready` or the reason it is not ready. It exits 1 when `ready` is false.
- `load_system(home)` reads and checks `system.yaml` and raises `SetupError` naming `python3 -m features setup system` when the file is absent, malformed, or of another schema or version.

#### The project skeleton

`setup/skeleton.py` and the templates in `setup/project_template/`, used by project setup. It runs no command.

- A new project follows the sample project's flat layout. The skeleton plans `README.md` (first heading `# Project guide`, then each product with its source and `make <product>`, then where computed results, references, data, notes, and verification results go, and the date it was set up), `numbers.yml` (`numbers: {}`), `pipeline.yaml` (`helpers: []` and `steps: []`), `params.yaml` (`{}`), `acquisition.yaml` (`raw: []`), `verification/README.md` (first heading `# Verification results`), an empty `refs.bib` or a copy of the citation export when that file exists, and one source per product from `manuscript.md` (for `docx`) or `slides.md` (for `revealjs`), with the title in the front matter as a quoted YAML string. Each YAML file starts with a comment and gains no `schema` key, since other parts read it. No written file holds `@@` or a placeholder's two opening braces, and the product sources hold no numeral.
- It writes no `.gitignore`, no `Makefile`, and no notes. Project setup adds each product's rule with `ospipe add-product`, installs the notes with `ospipe install-notes`, and appends only the rule from `makefile_text`.
- `Product(name, source, to)`, where `name` matches `[a-z][a-z0-9_]*` and is not `manifest` or `emit`, `to` is `docx` or `revealjs`, and `source` is a path inside the project that the skeleton does not use for another file. Names and sources are unique. `DEFAULT_PRODUCTS` is the manuscript, `manuscript.md`, as `docx`.
- `plan_skeleton(project_dir, title, products, citation_export, now)` gives a list of `PlannedFile(path, data)`, with `path` relative to the project and `data` as bytes, and writes nothing. An empty title takes the folder's name. It raises `SkeletonError` with `.problems` naming every problem at once, for the products and for a title that is not one line, holds a placeholder's opening braces or `@@`, or reads as one of the two guides' headings.
- `write_skeleton(project_dir, planned)` makes the folders and opens each file with mode `x`, so it writes only a file that is absent and never writes through a link. It gives `SkeletonResult(created, kept, messages)`, with one message for each file kept.
- `makefile_text(products, citation_export, project_dir)` gives `MakefileText(text, messages)`, the text to append to the build file. With an export it is a comment, the rule `refs.bib: <export>` whose recipe copies the export to `refs.bib`, and the line `<each product's name>: refs.bib`, so make copies the export whenever it is newer and each build uses the scholar's current library. The text is empty with a message when the export is missing, when its path holds a character make cannot take in a file name (a line break, `:`, `%`, `\`, `*`, `?`, or `[`), or when `refs.bib` exists and differs from the export. It is empty with no message when there is no export.

#### setup project

`python3 -m features setup project DIR [--home DIR] [--answers FILE] [--title TEXT] [--product NAME:SOURCE:FORMAT ...]`, once per project, in `setup/project.py`. `setup/GUIDE.md` tells a scholar, or an AI session in the scholar's harness, how to run both setup commands.

- It loads `system.yaml` from the features home (found as for system setup) and refuses, naming `python3 -m features setup system`, when it is absent or malformed. It runs the other layers from the `workflow_root` that file records.
- Answers come from the `--answers` YAML file and the flags, where a flag wins over the file. With no answers file and a terminal, it asks for each field the flags did not give. Otherwise it takes the defaults. The fields are `title` (by default the folder's name), `products` (a list of mappings with `name`, `source`, and `to`, by default the manuscript, and `NAME:SOURCE:FORMAT` on the command line), and `citation_export` (by default the one in `system.yaml`, with an empty value for none). Any other field is refused.
- It plans the skeleton first and refuses, creating nothing, on a bad title or bad products, or when DIR is a file. Then it makes DIR, writes the skeleton, and runs `ospipe install-notes --project DIR`. When DIR has no `Makefile`, it runs `ospipe add-product --name NAME --source SOURCE --to FORMAT --bib refs.bib --tables-dir .` in DIR for each product and appends the text of `makefile_text`. A `Makefile` that exists is kept as it was and gets no rule. It writes no `check` rule. Before it makes DIR it stops, naming `python3 -m features setup system`, when the `workflow_root` holds no `ospipe/ospipe`. A failed `install-notes` or `add-product` stops setup with that command's error. Then it reads the products the build file names with `ospipe products --json` in DIR. Each answered product the build file lacks is missing, with the `PYTHONPATH=<workflow root>/ospipe python3 -m ospipe add-product ...` line, run in DIR, that adds its rule. An answered product the build file names with another source or format differs, and setup prints how the build file builds it, since add-product cannot add a rule whose name is taken. Each problem `ospipe products` gives is kept, and a nonzero exit with no problem named is itself a problem.
- It runs `ospipe check --manuscript SOURCE --manifest numbers.yml --tables-dir .` in DIR on each product's source.
- It runs no git and refuses no folder for being excluded (reconciliation, Track F). It reads the run command of the GitHub procedure from the knowledge base entry `procedures-ops-github` in `<workflow root>/audit_layer/kb/corpus/`, and prints it when that entry exists.
- It prints the files created and kept, the notes written and kept, the rules added to the build file, each check's result, `make <product>` for each product the build file names that differs from no answer and has no problem, the add-product line for each missing product, how the build file builds each product that differs, each problem `ospipe products` gives, the GitHub procedure's run command, the later connections, and `Ready` or `Not ready` with the reason. It lists each kept file once. It exits 1 when a check fails, a product is missing or differs, the build file has a problem, or setup stops, and 0 otherwise.

### organize

Filled by the organizer's steps.

#### organize scan

`python3 -m features organize scan DIR [--home DIR]`, in `organizer/inventory.py`. It writes the organizer's inventory of a project's files to `<DIR>/.organizer/inventory.json` and changes no project file.

- `read_map(project_dir, root=None, runner=run_layer)` gives `ProjectMap(products, referenced, problems)`. The products are those `ospipe products --json` gives when run in DIR through the layer runner, as mappings with paths relative to DIR (reconciliation, Track F). `referenced` lists, in order, the files each product names after `--manifest`, `--bib`, `--csl`, and `--reference-doc`. A missing `Makefile`, each problem ospipe finds, and output that is not ospipe's JSON are each a problem, never an error.
- `read_declared(project_dir)` gives the set of files `pipeline.yaml` names (its helpers, and each step's script, inputs, and outputs), the raw files in `acquisition.yaml`, and the `from` files in `numbers.yml`, as relative paths. A file that is absent or cannot be read adds nothing.
- `scan_files(project_dir, project_map, declared)` gives a `FileEntry(path, size, sha256, kind, claims, archive_line, protected)` for each file, in path order. The walk leaves out `.git/` and `__pycache__/` in any folder, `.organizer/` and `ship/` at the top, and each product's builds folder. A link that leads to nothing is left out with a message.
- `kind` is the first that holds of `canonical` (a source the map names), `verification` (under `verification/`), `build_input` (`Makefile`, `numbers.yml`, `refs.bib`, `pipeline.yaml`, `params.yaml`, `acquisition.yaml`, and the referenced files), `declared`, `archived` (a markdown file whose first non-empty line after any front matter starts with `> ARCHIVE`), `lookalike` (a markdown file with no archive line whose title equals a canonical's title, or whose file name holds the canonical's name), `notes` (under `notes/`), and `other`. Titles and archive lines follow ospipe's layout contract. `claims` names the canonical a look-alike or archived file reads as, else null. `archive_line` is the archive line, else null. `protected` is true for `canonical`, `verification`, `build_input`, and `declared`, and for any file named `author_draft.md`, which is never a look-alike because the references and prose procedures read it.
- `read_builds(project_dir, project_map)`, in `organizer/sessions.py`, gives `(builds, problems)`. For each product's builds folder it reads `BUILDS.md` by its header row, so the seven-column ledger and the nine-column one with `verification` and `runs` both read. Each build is a mapping with `item` (`<product>/<version>`), `product`, `version`, `date`, `sha256`, `purpose`, `verification` and `runs` (`-` when the ledger has no such column), `file` (the build file's path relative to DIR, or null when there is none), and `file_ok` (the file's checksum matches its row). A ledgered file that is missing or changed, a row whose width differs from the header, and a `vNNN.docx` or `vNNN.html` file with no row are problems. It writes nothing.
- `read_sessions(audit_db, project_dir)`, in `organizer/sessions.py`, opens the audit database read only (`connect_read_only`, a `mode=ro` connection whose URI holds the path escaped, so a `#`, `?`, `%`, or space in the path cannot open another file) and reads only the `sessions` and `events` tables, never `transcripts` or the file store. The columns it reads are `SESSION_COLUMNS` and `EVENT_COLUMNS`, the slice's names. It lists each session whose current row (one no later row supersedes) has a `project` that is DIR or inside it, with `ran_here` true, and each session elsewhere with an event, on any of its rows, whose `role` is `produced` or `edited` on a file inside DIR, with `ran_here` false. A superseded event row is left out. Each session is a mapping with `harness`, `harness_session_id`, `ran_here`, `started_at`, `ended_at`, `tools`, and `files`, each file a mapping of `path` (relative to DIR), `role`, `verb`, and `present`, in path order, taken from the first event that produced or edited it. An event's relative path is read against the project of the session row it belongs to. Paths are compared as real paths. A missing database gives an empty list. This one function holds the reading of session records (track F choice 18), so a handoff copy can replace it.
- `build_inventory(project_dir, now, root=None, runner=run_layer, audit_db=None)` gives the record with `schema` (`organizer-inventory`), `schema_version` 1, `inventory_id`, `project` (the folder's real path), `scanned_at`, `map` (`products`, `referenced`, and `problems`), `files`, `builds`, `build_problems`, `sessions`, and `messages`. Each file entry also has `sessions`, the ids of the listed sessions that produced or edited it. With no `audit_db` no sessions are read. A database that is missing or cannot be read lists no sessions and leaves a message. `inventory_id` is the sha256 of the files' paths, sizes, checksums, and kinds, the build rows, and the sessions' harness and ids, with no times or absolute paths, so an unchanged project gives the same id wherever it lies. `write_inventory(project_dir, record)` writes it and gives the path.
- The command loads `system.yaml` from the features home and refuses without it, naming `python3 -m features setup system`. It runs ospipe from the `workflow_root` that file records and reads `audit.sqlite` in the `audit_home` it records, read only (reconciliation item 4). It refuses a DIR that is not a folder. It refuses no folder for being excluded and reads no audit settings (reconciliation item 3). It prints the count of files of each kind, each look-alike with the canonical it reads as, the build file's problems, the count of builds and their problems, the count of sessions with each one's harness and id, the messages, and the path and id of the inventory it wrote. It exits 1 when it refuses and 0 otherwise.

#### organize check

`python3 -m features organize check DIR PROPOSAL [--home DIR]`, in `organizer/proposals.py`. It checks a proposal the scholar's AI session wrote and changes nothing.

- A proposal is a YAML mapping with `schema` (`organizer-proposal`), `schema_version` 1, `proposed_by` (such as `ai:claude_code:<session id>` or `scholar:<name>`), `inventory_id` (copied from the inventory it was written from), and `changes`, a list. Each change has `id`, `op`, `reason`, and the fields of its operation. `move` has `path` and `to`. `archive_line` has `path` and `superseded_by`. `mark` has `item_kind` (`file`, `build`, or `session`), `item` (a path, `<product>/<version>`, or a harness session id), `mark` (`unused`, `superseded`, `belongs_to`, or `note`), and `value` (the replacing item, the project folder, or the note), which `unused` does without.
- `load_proposal(path)` reads the file and raises `ProposalError` naming it when it cannot be read, is not YAML, or is not a mapping.
- `check_proposal(project_dir, proposal, inventory)` gives a list of `Problem(change_id, rule, message)`, empty when every change can be applied, against `inventory`, a fresh record from `build_inventory`. It refuses a wrong `schema` or `schema_version`, a missing `proposed_by`, `changes` that is not a list, a change that is not a mapping, a missing, repeated, or not text `id`, and a missing or empty `reason`. An `inventory_id` that differs from the fresh one refuses the whole proposal, since the project changed after the AI read it, and the changes are then not checked one by one. An `op` of `delete`, `remove`, `rm`, `unlink`, or `overwrite` gets "the organizer never deletes, so mark the item unused instead", and any other op the organizer does not have is refused.
- A `move` needs a `path` that is a file in the inventory and not protected, so a build, which the inventory does not list, is never moved. Its `to` must lie inside DIR once links are followed, must not exist, must not lie under a file, must lie outside `.organizer/`, `verification/`, each product's builds and verification folders, and any `.git/` folder, matched in any case since folder names on macOS ignore case, and must not be, lie under, or lie above the target of an earlier change. A file moved by an earlier change is not moved again. A `to` that lies in an excluded folder is not refused (reconciliation item 3).
- An `archive_line` needs a `path` that is a markdown file of kind `lookalike` and a `superseded_by` that is a source the map names, and its file must not be moved away by an earlier change.
- A `mark` needs an `item` of its `item_kind` in the inventory (a file's path, a build's item, or a session's harness session id), a known `mark`, and a `value` for every mark but `unused`.
- `describe(change)` gives one plain line, the change's id, what it does, and its reason.
- The command reads the proposal, loads `system.yaml` from the features home (refusing without it, naming `python3 -m features setup system`), and rescans the project in memory with `build_inventory`, writing no inventory. It prints the proposal and the project, each change's line, then `No problems` or each problem with its change id, and `Nothing was changed`. It exits 1 on any problem or when it stops, and 0 otherwise.

#### organize apply

`python3 -m features organize apply DIR PROPOSAL --by NAME [--home DIR]`, in `organizer/apply.py`, with the journal, the content store, and the marks in `organizer/journal.py`. The scholar applies a whole proposal, editing the file first to drop any change.

- `keep_bytes(project_dir, data)` keeps content once in `<DIR>/.organizer/originals/<sha256>`, gives the sha256, leaves content already kept as it is, and never removes anything. `kept_bytes(project_dir, sha256)` gives the bytes back, or None when the store lacks them or they no longer match their name.
- `append_entry(project_dir, fields, now)` appends one JSON object per line to `<DIR>/.organizer/journal.jsonl` and gives its id, `j0001`, `j0002`, and so on. Each entry holds `schema_version` 1, `entry`, and `at`, then the fields in the order given, and `undoes` (null unless given) last. An apply entry's fields are `by`, `proposed_by`, `proposal_sha256` (of the proposal file's bytes), `change_id`, `op`, `reason`, and the operation's fields. A `move` records `path`, `to`, and `sha256`. An `archive_line` records `path`, `superseded_by`, `line`, `before_sha256`, and `after_sha256`. A `mark` records `item_kind`, `item`, `mark`, and `value`. Earlier lines are never touched. `read_journal(project_dir)` gives the entries in order, an empty list when there is no journal or it is empty, and raises `JournalError` naming the line that is not a journal entry, and also when the journal does not end with a line break, since its last line was then cut short. Apply and undo read the journal before they change any file, so such a journal stops them with no file changed.
- `apply_proposal(project_dir, proposal_path, by, now, root=None, runner=run_layer, audit_db=None)` gives `ApplyResult(problems, applied, not_applied, inventory_path)`. It reads the journal, rescans the project, and runs `check_proposal`. With any problem it applies nothing and writes nothing. Otherwise the changes apply in order and each is journaled as soon as it succeeds. On a failure the failed change and each after it are listed in `not_applied` with why, and `marks.yaml` and the inventory are still written. A change fails when it is refused, on an `OSError`, and when the layer runner raises `LayerMissing` or times out during an archive line. An empty `by` raises `ApplyError`.
- A `move` makes the target's folders and renames the file, refusing a target that appeared after the check. An `archive_line` keeps the file's bytes, runs `ospipe archive PATH --by CANONICAL --date YYYY-MM-DD` in DIR through the layer runner with the date of `now` (reconciliation, Track F), keeps the new bytes, and records the line ospipe wrote, `> ARCHIVE <YYYY-MM-DD>: superseded by <canonical>` as the first line after the front matter, or at the top when there is none. A `mark` changes no project file.
- After applying it writes `<DIR>/.organizer/marks.yaml` (`schema` `organizer-marks`, `schema_version` 1, and `marks`, each with `item_kind`, `item`, `mark`, `value`, `reason`, `entry`, `by`, and `proposed_by`, for every mark no later entry undid, in journal order) and a fresh inventory.
- The command loads `system.yaml` from the features home (refusing without it, naming `python3 -m features setup system`). With a problem it prints each change's line, each problem, and `Nothing was applied`, and exits 1. Otherwise it prints each applied change with its journal entry, each change not applied with why, and the paths of `marks.yaml` and the inventory. It exits 0 when every change applied and 1 otherwise.

#### organize undo and organize log

`python3 -m features organize undo DIR ENTRY --by NAME [--home DIR]` and `python3 -m features organize log DIR`, in `organizer/undo.py`. There is no redo, since the scholar applies the proposal again after a fresh scan.

- `undo_entry(project_dir, entry_id, by, now, root=None, runner=run_layer, audit_db=None)` gives the id of the undo entry it appends. It raises `UndoError` and changes nothing for an empty `by`, a project with no journal, an unknown entry, an entry already undone (naming the entry that undid it), and an undo entry.
- A move is undone when the file at `to` still has the recorded checksum and `path` is free, by moving it back. The folders the move made are left in place. An archive line is undone when the file still has `after_sha256`, by writing back the original bytes from `.organizer/originals/` under `before_sha256`. A mark needs no file change. Any other state, a file gone, changed, or in the way, or original bytes missing from the store, is refused with what changed, and the bytes of both versions stay in `.organizer/originals/`.
- The undo entry holds `by`, `proposed_by` and `proposal_sha256` as null, `change_id` of the undone entry, `op` `undo`, `reason` (`undo of <entry>`), the reversed fields, and `undoes`. A move's reversed fields swap `path` and `to` and keep `sha256`. An archive line's swap `before_sha256` and `after_sha256` and keep `path`, `superseded_by`, and `line`. A mark's are its `item_kind`, `item`, `mark`, and `value`. Then undo rewrites `marks.yaml`, where an undone mark no longer appears, and the inventory.
- `log_text(project_dir)` gives the journal as a table, with the entry, the time, who ran it, who proposed it, the operation, the item, the reason, and which entry undid it, then `Marks` and each current mark, or `none`. A project with no journal gives one line saying so.
- The undo command loads `system.yaml` from the features home (refusing without it, naming `python3 -m features setup system`), prints the undo entry and what it reversed, and the paths of `marks.yaml` and the inventory. It exits 1 when it refuses, with the reason on the error output, and 0 otherwise. The log command reads only the journal, prints `log_text`, and exits 0, or 1 when DIR is not a folder or the journal cannot be read.

#### The organizer's guide

`organizer/GUIDE.md` tells the scholar, and an AI session in the scholar's harness, to run `organize scan`, read `.organizer/inventory.json`, and write a proposal in `.organizer/proposals/<YYYY-MM-DD>_<n>.yaml` with only `move`, `archive_line`, and `mark`, each with a reason, copying `inventory_id` and naming the session in `proposed_by`. It says never to propose a deletion and to mark the item `unused` instead, to mark `author_draft.md` with a note rather than archive it (reconciliation, Track F), to run `organize check`, and to leave `organize apply` to the scholar's word. It shows how to undo and read the log, and holds one complete example proposal. A test parses every organizer command line in it with the organizer's commands and checks the example against a fresh scan of the organizer fixture.

### portal

Filled by the portal's steps.

#### The portal's sources

`portal/portal.yaml` names what the portal is built from, with paths from the workflow's folder, so nothing else enters the site. It holds `title` (`An AI-Enhanced Workflow for Verifiable Social Science`), `kb_corpus` (`audit_layer/kb/corpus`), `graphs` (`verification_procedures/graphs`), `home` (`features/portal/pages/home.md`, added in step F15), and `docs`, a list of `path`, `title`, `section` (`learn`, `implement`, or `critique`), and `optional`. The required docs are `verification_procedures/README.md` (learn), `features/portal/pages/implement.md`, `examples/sample_project/README.md`, `features/setup/GUIDE.md`, and `features/organizer/GUIDE.md` (implement), and `features/portal/pages/critique.md` (critique). The optional learn pages are `verification_procedures/AUTHORING.md`, `audit_layer/hooks/INSTALL.md`, `observability/CONTRACT.md`, `handoffs/README.md`, and `connections/README.md` (reconciliation, Track F).

`portal/sources.py` reads those sources and writes nothing.

- `load_entries(corpus_dir, root=None)` gives an `Item(kind, id, title, group, source, source_commit, updated, gist, markdown, consult_also, origin)` for each `<group>/<id>.md`, in file order, with `kind` `entry`. The next six come from the entry's heading of six keys between two lines of three hyphens, `gist` is the first paragraph after the title, `markdown` is the text after the heading, `consult_also` lists the ids the `## Consult also` section names, and `origin` is the file's path from the root. An entry with no heading, a heading not closed, or a heading key missing raises `PortalError` naming the file, since the entry checker owns the entries' form.
- `load_procedures(graphs_dir, root=None)` gives a `Procedure(stream, version, goal, entry, exit, nodes, edges, verification, origin)` for each `*.yaml` graph, in file order, with `origin` the graph file's path from the root (added in step F13, since procedure pages are named by the file's stem). `stream` is the graph's `stream`, or the file name when it has none. Each node is a mapping of `id`, `kind`, `does`, `invariant`, `foreach`, `where`, `role`, and `replay`, the `reads`, `reads_optional`, and `produces` file names from the graph's `contracts` file, the `implementations` that exist (`implementations/<stream>/<node>.py` or `.prompt.md` beside the graphs folder, as paths from the root), and `extra` with any other key. Each edge is a mapping of `from`, `to`, `rel`, `condition`, `guidance`, `pitfalls` (a list), `source`, and `check`, with any other key in `extra`. `verification` is true for `prose`, `citations`, `data`, and `build`. A graph that is not a mapping, or a contracts file that is named and missing, raises `PortalError` naming it.
- `load_docs(root, docs, warnings=None)` gives an `Item` for each listed doc that exists, with `kind` `doc`, `id` its path in lower case with each run of other characters a hyphen (`features-setup-guide`), `title` from the config, `group` its section, `source` and `origin` its path, `source_commit` `sha256:` and the first 12 characters of the file's sha256, `updated` null, and `gist` its first paragraph that is not a heading. A missing optional doc adds a warning, and a missing required one raises `PortalError`. A doc line with an unknown key, no path or title, a section not listed, or a path outside the workflow's folder is refused.
- `load_home(root, path, title)` gives the home page's `Item`, with `kind` `home`, `id` `home`, the config's title, `group` null, and `source`, `origin`, and `source_commit` as for a doc. A home file that is missing, unreadable, or outside the workflow's folder raises `PortalError`.
- `load_all(config_path, root=None)` gives `PortalSources(items, procedures, warnings, title, home)`, the entries and then the docs, the graphs, the warnings, the config's title, and the home page's `Item`, or null when the config names no `home`. A missing or unreadable config, a missing key, a `home` that is not a path, or a missing corpus or graphs folder raises `PortalError`.

#### The portal's pages and catalog

`portal/render.py` writes the site, which opens from disk with no server or network.

- `markdown_to_html(text, rewrite=None)` runs `pandoc --from markdown --to html5` with the text on standard input and drops a first line that is a level-one heading, since the page shows the title. With `rewrite`, the text goes through Pandoc's JSON form, and `rewrite(kind, target)` gives each link's or image's new target, or `None` to keep only its text. A missing Pandoc, or one that fails, raises `PortalError`.
- `page_html(item, site, body_html, depth)` gives a complete page, with `<!doctype html>`, a charset and a viewport meta, the item's title, the stylesheet by relative path, a header linking to the catalog and its Learn, Implement, and Critique sections, the item's source, source version, updated date (`none` when it has none), group, and origin, the body, and an empty `<section class="critique">` with `data-page-id` (the item's id), `data-title`, `data-source`, and `data-source-commit`. `site` is a `Site(title)`, and `depth` counts the folders between the page and the site's folder. Every value from a source is escaped.
- `write_site(sources, out_dir, now, root=None)` gives `SiteResult(pages, warnings)`. It writes `index.html`, the catalog, with a card per item (title, kind, group, and gist) under Learn, Implement, and Critique. Entries sit under Learn in a group of cards per knowledge base group, and docs sit under their section as Documentation. Each entry has `entries/<id>.html`, where each Consult also id becomes a link to that entry's page, and each doc has `docs/<id>.html`. In any page, a relative link to a listed entry's or doc's file points at its page, keeping its fragment. Links to the web, to a fragment, or to mail are kept. Any other link, and every image, becomes its text and a warning, since the site holds no file of its own beside the pages and the stylesheet. It copies `assets/portal.css` byte for byte and writes `site_manifest.json` with `schema` `portal-site`, `schema_version` 1, `built_at` from `now`, `pages` (each file of the site with its `path`, `origin`, and `sha256`, where the catalog's origin is null and the stylesheet's is `features/portal/assets/portal.css`), and `sources` (each source file's `origin` and `sha256`). `pages` in the result lists the HTML pages, and `warnings` holds the sources' warnings and each link or image the site could not keep.
- The out folder must be absent, empty, or an earlier portal build, one holding a `site_manifest.json` of schema `portal-site`. For an earlier build, the files its manifest lists are removed and the site is written again, so a page whose source is gone is gone too. Any other folder, or a manifest naming a path outside the folder, is refused and left as it is. Every page is made before the folder is touched.
- `assets/portal.css` sets readable type, light and dark colors by `prefers-color-scheme`, a visible focus outline, and a layout that works at phone width. It fetches no font or image.

#### The portal's procedure pages

`portal/procedures.py` gives `procedure_body(proc)`, the body of one procedure's page. It shows the stream, version, goal, and first and last steps, then each step in file order as `<li class="step" id="step-<id>">` with its id, kind, what it does, its invariant, `foreach`, `where`, and `role` when present, the files it reads (and those it reads when present, when it has any) and produces from its step contract, and its implementation files. The step's outgoing edges follow it, each in a `<details class="edge">` block with the next step, the relation, the condition, the guidance, each pitfall, the source, and the `check` when present. An edge from no listed step is shown after the steps. All graph text is escaped, and no diagram is drawn.

`write_site` writes `procedures/<stem>.html` for each graph, named by the graph file's stem (reconciliation, Track F), so `ops_github.yaml` and `ops_hpc.yaml`, which share the stream `ops`, each have a page. A procedure page's item has kind `procedure`, id the stem, title `The <stem> procedure`, source and origin the graph file, source version `sha256:` and the first 12 characters of the graph file's sha256, and gist its goal. Its cards sit under Learn, the four streams as Verification procedures and every other graph as Other procedures, ahead of the entries. A doc's relative link to a graph file points at its procedure page.

#### Search, the critique box, the portal's own pages, and the portal command

`python3 -m features portal build [--config FILE] [--out DIR]`, in `portal/render.py` (step F15). The config is `features/portal/portal.yaml` and the out folder `features/portal/_site/` unless given, both in the workflow's folder, and `features/.gitignore` holds `portal/_site/`. The command loads the sources, writes the site, and prints the page count, each warning, and the path of `index.html`. It exits 1, with the reason on standard error and nothing written, when a source or the out folder is refused, and 0 otherwise.

- When the config names a `home`, its text, with its first level-one heading dropped and its links pointed at their pages, opens `index.html` in `<div class="home">` above the catalog. A doc's relative link to the home file points at `index.html`, and the home file is listed among the manifest's `sources`.
- Every page gains, in its header, a search box (`<form class="search" role="search" hidden data-root="<path to the site's folder>">`), and at the end of its body `<script src="<root>search_index.js">` and then `<script src="<root>assets/portal.js">`. The catalog also gains buttons (`data-section` `all`, `learn`, `implement`, and `critique`) that show one section, and a line that says how many pages match. The box and the buttons are hidden until the script shows them.
- `search_index.js` is written as `window.PORTAL_INDEX = <JSON list>;`, a script rather than a JSON file so the site works opened from disk. It has one row per item page (every page but the catalog), each with `id`, `title`, `kind`, `group`, `section`, `gist`, and `url` (the page's path from the site's folder), in ASCII JSON. `assets/portal.js` is copied byte for byte. The manifest lists `search_index.js` with origin null and `assets/portal.js` with origin `features/portal/assets/portal.js`.
- `assets/portal.js` uses no library and no network. On the catalog, the search box hides each card whose row does not hold every word of the query in its title, gist, group, or kind, and the buttons hide every section but the one chosen. On any other page, the box lists the matching pages as links. On every item page it fills the critique section with fields for the name, the section (`whole page` or one of the page's headings), and the text, and two buttons. Copy puts the critique on the clipboard, and Save downloads it as `critique_<page id>_<YYYY-MM-DD>.yaml`. A critique is YAML with `schema` (`portal-critique`), `schema_version` 1, `page`, `title`, `source`, `source_commit`, `section`, `by`, `date`, and `text` in that order, each text a double-quoted string. It needs a name and a text. Nothing collects critiques.
- `portal/pages/home.md` says what the portal holds, gives the four streams with their tools and procedures as in the proposal's Table 1, each procedure linked to its page, and says where to start. `portal/pages/implement.md` gives the setup commands, then the offline commands that build the sample project and run the four procedures, and points to the sample project's page. `portal/pages/critique.md` says how to write and save a critique and that every page shows its source and version so a critique names what it is about.

## Frozen promises

- The features never import the code of `ospipe`, `audit_layer`, `verification_procedures`, `vg`, `_lib`, `observability`, or `connections`. A test parses every file of the package and fails on any such import.
- Each record file whose form the features define carries `schema` and `schema_version`, and each journal line carries `schema_version`. Files written in a form another part reads keep exactly that form and gain no such keys.
- Setup never overwrites, changes, or removes a file that exists, and reports each one it kept. The exceptions are its own `system.yaml`, which each run of `setup system` writes again while keeping every excluded folder recorded before, and `provider.yaml`, which `setup system` writes again through `connections provider set` when a model service is given, keeping an earlier output limit the answers do not replace. Setup adds the excluded folders to the audit layer's settings file through that layer's own command and never removes one (step S2).
- The organizer never deletes. Its operations are `move`, `archive_line`, and `mark`, and every applied change can be undone.
